# منفّذ AAS: GitHub Actions والخادم الخاص

هذه الحزمة تنفّذ تحليل ملفات فعليًا، وتطبّق patch محليًا عند التصريح، وتشغّل أوامر اختبارات محددة في ملف إعداد راجعه المسؤول. تُرسل أدلة المراحل إلى لوحة AAS الخاصة. وجود الحزمة أو تنزيل إعداد الاتصال لا يعني أن Actions أو الخادم الخاص اتصلا أو نجحا في البناء؛ يظهر ذلك بعد تشغيل يصل منه إيصال موثّق.

المنفّذ يتصل باللوحة عبر HTTPS صادر فقط. الخادم الخاص داخل الشبكة المحلية لا يحتاج إلى فتح منفذ HTTP أو استقبال اتصال من اللوحة. تعذّر الوصول إليه من بيئة السحابة؛ تُجرى خطواته التالية على الجهاز أو شبكته عند توفرهما.

## الملفات

- `integrations/runner/runner.mjs`: برنامج Node مستقل بلا حزم خارجية.
- `integrations/runner/config.example.json`: مثال أوامر Node وpatch يختاره المسؤول.
- `integrations/runner/config.android.example.json`: مثال حقيقي لتجميع Kotlin واختبارات Android.
- `integrations/runner/templates/aas-executor.yml.example`: قالب Actions يُنسخ عمدًا إلى `.github/workflows/aas-executor.yml` في المستودع الذي سيُنفَّذ.
- `integrations/runner/runner.test.mjs`: اختبارات المطوّر بمستودعات Git مؤقتة؛ تحتاج ملفات `server/state.mjs` في مشروع مركز القيادة، ولا تُنسخ إلى مشروع Android.

## التشغيل على الخادم الخاص

يتطلب التشغيل Git وNode 24، ومجلد مستودع محلي يحتوي الالتزام SHA الكامل الذي حدّدته في مسار التنفيذ. ملفات الإعداد والـpatch محلية داخل مجلد المستودع أو جذر أدوات موثوق يحدده المسؤول بخيار `--config-root`. لا تُحمّل patches من رابط، ولا تُنفّذ أوامر قادمة من API.

1. نزّل حزمة التنفيذ وإعداد الاتصال الخاص من شاشة ربط المنفّذ في لوحة AAS. احفظ ملف الاتصال خارج المستودع، مثل `/home/amer/.config/aas/connection.json`، بصلاحية قراءة للمستخدم المسؤول فقط. يتضمن الملف أسرار اتصال؛ لا ترفعه إلى Git أو ترسله في المحادثة أو سجلات الدعم.
2. ضع `runner.mjs` وملف إعداد عام في المستودع المقصود. انسخ المثال إلى `integrations/runner/config.json`، وغيّر `repository` إلى `owner/repository` المطابق لمسار AAS. حدّد كل خطوة باستخدام `stepIndex` يبدأ من صفر، أو `stepId` بعينه. لا تستخدم الاثنين معًا.
3. شغّل الأمر التالي من حساب تشغيل مخصص. استبدل القيم الوصفية بقيم مسار التنفيذ الحقيقي:

```bash
chmod 600 /home/amer/.config/aas/connection.json
node integrations/runner/runner.mjs \
  --repo /home/amer/projects/my-store \
  --config integrations/runner/config.json \
  --connection-config /home/amer/.config/aas/connection.json \
  --workflow workflow-REPLACE \
  --source-revision REPLACE_WITH_FULL_COMMIT_SHA \
  --work-dir /home/amer/aas-jobs/new-job-directory
```

يجب أن يكون مجلد `--work-dir` جديدًا وخارج المستودع الأصلي. يتوقف البرنامج بدل الكتابة فوق مجلد سابق. ينشئ نسخة Git منفصلة عند SHA المثبّت؛ تبقى شجرة المستودع الأصلية كما كانت.

إعداد الاتصال هو JSON يضم `baseUrl` و`runnerToken` و`siteAccessToken`. يقابلها `AAS_BASE_URL` و`AAS_RUNNER_KEY` و`AAS_SITES_AUTHORIZATION` في بيئة التشغيل. يمكن استعمال المتغيرات بدل الملف؛ القيم الموجودة فيها تتقدم على قيم الملف. تُرسل المفاتيح في `X-AAS-Runner-Key` و`OAI-Sites-Authorization` إلى أصل HTTPS واحد، دون إعادة توجيه. لا يُستخدم مفتاح الخدمة العام للمتجر.

لخطوة تتضمن تغييرًا، أضف `patch` نسبيًا إلى المستودع في الإعداد ومرّر `--apply` عمدًا. يتحقق البرنامج من patch ثم يطبقه ويصنع التزام Git محليًا في النسخة المنفصلة. بلا هذا الخيار لا يصنع التزامًا، ويسجّل مرحلة التغيير متوقفة بسبب غياب التصريح. `--advance` يصرّح باعتماد الانتقال بعد نجاح التحقق الحالي؛ أضف `--all` لمعالجة الخطوات اللاحقة المحددة في ملف الإعداد في النسخة نفسها. لا يوجد أمر push داخل المنفّذ.

## إعداد Android الحالي

المثال يستخدم Java 21 وGradle 9.3.1. المشروع الذي فُحص يستخدم AGP 9.1.1 وKotlin 2.2.10 وSDK 36.1، ولا يحتوي Gradle wrapper؛ لذلك يثبّت قالب Actions إصدار Gradle صراحة. جهّز الأدوات نفسها على الخادم الخاص مع Android SDK وتراخيصه، وأتح `JAVA_HOME` و`ANDROID_HOME` أو `ANDROID_SDK_ROOT` و`PATH` للحساب. لا يثبّت المنفّذ حزمًا أو يقبل تراخيص تلقائيًا.

أمر المثال الفعلي هو:

```json
["gradle", ":app:compileDebugKotlin", ":app:testDebugUnitTest", "--no-daemon"]
```

استخدم نمط «تحليل وتحقق» إذا كان المطلوب اختبار المصدر بلا patch. غياب SDK أو Gradle أو فشل التجميع يعطي نتيجة فشل فعلية؛ لا توجد نتيجة نجاح بديلة. تأكد أن مخرجات البناء مغطاة في `.gitignore`؛ أي ملفات مصدر أو ملفات غير متتبعة جديدة بعد الاختبارات تغلق بوابة التحقق.

## GitHub Actions

راجع وأضف ملفات المنفّذ والإعداد والقالب إلى المستودع المطلوب أولًا. يجلب القالب نسختين منفصلتين: أدوات التنفيذ وملفات الإعداد من SHA الموثوق لملف workflow داخل `.aas-tooling`، والمصدر المراد اختباره عند `source_sha` داخل `source`. لذلك يمكن فحص التزام أقدم لا يحتوي ملفات المنفّذ. مسار `config_path` والـpatch نسبيان إلى جذر الأدوات؛ الخيار الصريح `--config-root` يفصل ذلك عن المصدر. القالب يستخدم `workflow_dispatch` فقط، وأذونات `contents: read`، وcheckout بلا حفظ بيانات الدخول، ولا يدمج PR أو يدفع التزامات. يجهّز أدوات Android قبل استدعاء المنفّذ. يُحمّل الملفات الناتجة كـartifact فقط عند اختيار `upload_artifacts` صراحة، وهو معطّل افتراضيًا.

أنشئ بيئة GitHub اسمها `aas-executor` مع مراجعين مطلوبين، ثم أضف أسرار البيئة:

| GitHub environment secret | مصدره |
| --- | --- |
| `AAS_BASE_URL` | `baseUrl` من إعداد الاتصال |
| `AAS_RUNNER_KEY` | `runnerToken` |
| `AAS_SITES_AUTHORIZATION` | `siteAccessToken` |

لم تسمح صلاحية GitHub المتاحة أثناء التجهيز بإدارة أسرار Actions؛ أعادت العملية `403`. يلزم إعداد هذه الأسرار من حساب مخوّل قبل تشغيل القالب. لا يعني إنشاء ملف workflow أنه أصبح متصلًا.

أدخل معرّف مسار AAS وSHA كاملًا وملف الإعداد في Run workflow. خيارات `apply` و`advance` و`all_steps` تبدأ معطّلة. لا تعرض الأسرار في المدخلات. لا تضف مشغّل `pull_request` إلى هذا القالب؛ لا تُسلّم أسرار اللوحة لكود أو إعداد غير مراجع. البرنامج ينفّذ الكود المحدد فعليًا؛ شغّله بحساب أو آلة مؤقتة مخصصة، لأن تنقية بيئة العمليات الفرعية لا تعزل الشيفرة عن ملفات الجهاز أو شبكته.

لتشغيل القالب على جهازك ضمن Actions غيّر `runs-on` إلى `[self-hosted, linux, aas-private]` بعد تسجيل جهاز مخصص بهذه العلامة. تسجيل GitHub runner منفصل عن إعداد اتصال AAS. ويمكن استخدام CLI مباشرة دون تسجيل الجهاز في GitHub.

## الأدلة وحدود النشر

يفحص البرنامج الملفات المتتبعة فعليًا، ويحفظ بصمة لكل ملف وبصمة manifest وحالة Git ونطاق الفحص. عدد `TODO/FIXME` جرد نصي فقط؛ لا يمثل فهمًا دلاليًا أو مراجعة ذكاء اصطناعي. لا يتبع روابط الملفات الرمزية، ولا يفحص محتوى submodules غير المهيأة. حد التحليل ٢٠ ألف ملف، و١٦ MiB لكل ملف، و١٢٨ MiB إجمالًا.

تُشغّل الأوامر باستخدام argv و`shell: false`؛ لا يُعاد تفسير `$()` أو `;` داخل الوسائط. لا ترث عمليات الاختبار مفاتيح AAS أو GitHub؛ تُمرر مسارات أدوات البناء الأساسية وHOME مستقل فقط. تُحجب قيم مفاتيح البيئة وملف الاتصال المعروفة من سجلات الأدلة ووسائط الأوامر المعروضة. لا تطبع مفاتيح أخرى أو معلومات شخصية من الاختبارات؛ تبقى مراجعة السجلات قبل مشاركتها لازمة.

يحفظ مجلد `artifacts` تقرير التحليل وفرق الشيفرة وسجلات الاختبارات وبصماتها. إرسال المراحل يقتصر على مقتطفات محدودة وبصمات؛ حد السجل المحلي ٤ MiB لكل أمر، مع وسم الاقتطاع وبصمة المخرجات المستلمة كاملة. يُرسل رمز الخروج الفعلي؛ المهلة أو تعذّر بدء العملية لا يعدان نجاحًا. أي اختلاف في HEAD أو حالة المصدر بعد الاختبار يجعل التحقق فاشلًا.

عند إنشاء تغيير يوجد أيضًا `local-changes.bundle` يحفظ الالتزامات المحلية الجديدة بالنسبة إلى SHA الأصلي. هذا الملف ليس نشرًا إلى GitHub. يحتفظ المنفّذ به للاستعراض والاستعادة؛ لا ينشئ PR أو commit في المستودع الأصلي. نشر التغييرات أو دفعها يحتاج إجراءً لاحقًا يقرره المسؤول. حتى ذلك الوقت يظهر الدليل التزامًا محليًا، وتبقى نسخة GitHub كما هي.

كل إيصال يستخدم معرّفًا فريدًا ومراجعة الحالة ومراجعة الخطوة. الخادم يفرض ترتيب التحليل والتغيير والتحقق ومطابقة المصدر. التعارض `409` يوقف التشغيل ولا تُعاد الكتابة تلقائيًا. افحص النسخة المحلية والسياق في اللوحة قبل إعادة محاولة صريحة؛ إذا أصبح SHA المطلوب التزامًا محليًا غير منشور، استخدم النسخة المحتفظة به أو استعد الحزمة، ولا تغيّر SHA في اللوحة إلى مراجعة أخرى لتجاوز البوابة.

اختبار حزمة المنفّذ داخل مشروع مركز القيادة:

```bash
node --test integrations/runner/runner.test.mjs
```
