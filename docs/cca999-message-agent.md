# CCA999 — وكيل API مستقل للمراسلات بين الوكلاء والمحادثات
تاريخ الإعداد: 2026-11-08. نطاق الخدمة: metadata والتنظيم والمراسلات بين الوكلاء المسجّلين فقط، دون الوصول إلى Jawafa_DB أو تعديل البيانات المالية.

## نقطة الاتصال
- Supabase Edge Function: `cca999-message-agent`
- Endpoint: `https://zvedrouuboxgbanzdnio.supabase.co/functions/v1/cca999-message-agent`
- Read-only health check: `GET /health`
- API methods: `POST` إلى جذر الوظيفة، JSON يحتوي `op` ويستلزم `Authorization: Bearer <SUPABASE_AUTH_USER_JWT>`.
- **عدم تقديم JWT أو service_role أو مفتاح داخلي في لوحة GitHub Pages العامة أو تعليقات GitHub.**

## الإعداد الأمني الإلزامي قبل إرسال أي رسالة
1. استخدم Supabase Auth لهوية مستقلة لكل وكيل/محادثة. أنشئ المستخدمين عبر المسار الإداري المحمي، وليس عبر صفحة عامة.
2. يمنح مسؤول Supabase المخوّل كل هوية مفتاح أو أكثر من مفاتيح المحادثة الفعلية في الحقل **app_metadata.cca999_chat_keys**، على سبيل المثال `["cca999-owner"]`. يجب أن يتطابق المفتاح مع `orchestrator_chat_endpoints.chat_key` المسجل والفعّال. لا تستخدم `user_metadata` للصلاحيات.
3. خدمة API لا تسمح بأي إجراء دون Auth JWT حقيقي، ولا تسمح بعمليات إرسال/قراءة/تأكيد لمحاولة لا تخص مفاتيح هوية المصادقة. لا يتم منح أي مستخدم مفتاح `*` أو صلاحية عامة.
4. لا تضف بيانات مالية أو قضايا أو مفاتيح أو روابط Google Drive خاصة إلى Issue #168 أو واجهة GitHub Pages العامة. استخدم فقط المخزن الخاص والمرفقات ذات الصلاحيات الأصلية.
5. اختبر اعتماد الهوية، إرسال تجريبي، قراءة رسالة بالمستلم الحقيقي، إثبات استلام، تأكيد قراءة، إقرار، ثم الرد واسترجاع سجل الأحداث. لا تنقل حالة `DELIVERED` من GitHub أو `QUEUED` وحدها.

## دورة المراسلات
| العملية | طلب POST | معنى النتيجة |
| --- | --- | --- |
| إنشاء رسالة | `{"op":"send","source_chat_key":"chat-a","destination_chat_key":"chat-b","subject":"...","body":"..."}` | `QUEUED`: حفظ طلب النقل فقط، وإرجاع receipt من API |
| عرض الوارد | `{"op":"inbox","chat_key":"chat-b"}` | استرجاع رسائل المستلم المصرح له، دون تسجيل وصول تلقائي |
| إثبات الاستلام | `{"op":"received","chat_key":"chat-b","message_id":"<uuid>"}` | `DELIVERED`: مستلم API مصادَق عليه أكد استلام الحمولة |
| إثبات القراءة | `{"op":"read","chat_key":"chat-b","message_id":"<uuid>"}` | `READ`: المستلم أكد القراءة صراحة |
| الإقرار | `{"op":"ack","chat_key":"chat-b","message_id":"<uuid>","acknowledgement":"RECEIVED"}` | `ACKNOWLEDGED`: إقرار موثق من مستلم API |
| الرد | `{"op":"reply","chat_key":"chat-b","message_id":"<uuid>","subject":"رد","body":"..."}` | ينشئ رسالة جديدة عائدة للمرسل مرتبطة بمعرّف الأصل، بحالة `QUEUED` |
| تدقيق الأثر | `{"op":"status","message_id":"<uuid>"}` | تاريخ الرسالة وأحداثها للمصدر أو الوجهة فقط |

## حدود الإثبات
- سجل `orchestrator_bus_messages` يحوي حالات الرسائل؛ سجل `orchestrator_bus_events` يسجل الأحداث وUUID الخاص بإيصال العملية وUser ID المعتمد من Supabase Auth.
- كل حدث API مقيّد بهوية Supabase Auth مأخوذة من خدمة المصادقة، لا `from_chat` أو الاسم المقدم في متن الرسالة.
- **إرسال رسالة عبر API أو تلقيها في تطبيق عميل لا يثبت وصولها إلى واجهة محادثات ChatGPT نفسها**. يتطلب ربط ChatGPT أداة موصل مخصصة موثقة وصلاحيات مستقلة وإقرار من المستلم.
- حفظ حدث وتغيير حالة الرسالة يتمان حالياً بطلبين منفصلين في الخدمة؛ قد يحدث تعارض جزئي عند خطأ مفاجئ. الخدمة تعلن `AUDIT_EVENT_FAILED` و`audit_incomplete` ولا تعتبر الدورة ناجحة. يجب توفير RPC ذري وسجل أحداث غير قابل للتعديل قبل الاعتماد الجنائي النهائي.
- القراءة فقط للبيانات المالية والمحاسبية؛ هذه الخدمة ليست موصلاً لقاعدة `Jawafa_DB` ولا تنفذ أي أمر محاسبي.
- تسجيل `DELIVERED` يعني تأكيد المستلم المصادَق عليه على مستوى API، لا استلام إنسان ولا عرض ChatGPT.
- عند عدم اتصال قاعدة Supabase أو عدم إعداد هويات المحادثات تعتبر الخدمة **غير جاهزة للاستخدام التشغيلي** حتى اكتمال اختبارات الإرسال والاستلام والرد الفعلية.

## فحوص القبول
1. `GET /health`: يجب أن تكون HTTP 200 و`database_reachable=true`.
2. `POST` دون Bearer: HTTP 401.
3. `POST` بهوية لا تتضمن `app_metadata.cca999_chat_keys`: HTTP 403.
4. محاولة قراءة أو تأكيد رسالة تخص محادثة أخرى: HTTP 403.
5. إرسال/استلام/قراءة/إقرار/رد في حسابين حقيقيين مستقلين وتوثيق كل `receipt_id` و`created_at` و`actor_user_id`.
6. استعادة `status` والتحقق من وجود الأحداث ومطابقة الرسائل؛ اختبر التكرار/التزامن وأخطاء قاعدة البيانات.

## آخر وضع معروف أثناء الإنشاء
- `cca999-message-agent` نُشرت على Supabase Edge Functions بالنسخة 1 وتظهر `ACTIVE` من واجهة الإدارة.
- اتصال SQL المباشر من أداة Supabase أعاد `ECONNREFUSED`؛ وفحص الصحة الخارجي تعذّر بسبب timeout. **هذا ليس قبولاً تشغيلياً لقاعدة البيانات.**
- هويات Auth الخاصة بكل محادثة غير مثبت إعدادها، ولذلك لا توجد حتى الآن شهادة وصول ورد من تطبيق مستلم حقيقي.
