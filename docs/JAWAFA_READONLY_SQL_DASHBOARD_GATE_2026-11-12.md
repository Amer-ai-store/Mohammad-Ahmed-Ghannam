# Jawafa_DB → لوحة القيادة المركزية + JAWAFA ERP 2100

تاريخ القراءة المباشرة: 2026-11-12. **هذا سجل جاهزية، وليس شهادة ربط إنتاجي.**

## المسار الوحيد المسموح
`Jawafa_DB` على `JAWAFFASVR` ← حساب SQL `user_read` بصلاحيات SELECT للعروض المعتمدة فقط ← خدمة Windows محلية تستخدم ملف DPAPI من داخل الخادم ولا تطبع أو تصدّر الاعتماد ← واجهة API خاصة محمية بمصادقة المالك وTLS موثوق ← الشاشتان `#jawafa` و`#jawafa-2100`.

ممنوع اتصال المتصفح بـ SQL Server، أو تخزين كلمة مرور في GitHub/المتصفح أو استعمال `sa` في التشغيل اليومي، أو إصدار عمليات INSERT/UPDATE/DELETE أو محاكاة نتائج تحقق.

## الأدلة المفحوصة مباشرة في هذه الدورة
- خادم `JAWAFFASVR` متصل عبر وصلة الإدارة المصرّح بها، وخدمتا `MSSQLSERVER` و`SQLSERVERAGENT` تعملان.
- ملف `C:\ProgramData\Jawafa\Secrets\Jawafa_user_read_DPAPI.xml` موجود؛ أعاد استيراده محليًا نوع `PSCredential` واسم حساب ينتهي بـ `user_read`. **لا يعدّ هذا إثبات نجاح دخول SQL فعلي**.
- محاولة دخول SQL بمصادقة Windows الحالية: مرفوضة لأن حساب `JAWAFFASVR\Administrator` معطّل على SQL. لا تستنتج من ذلك حالة `user_read`.
- فحص SQL بالمستخدم `user_read` تحت شهادة موثوقة: **غير مثبت**، وفحوص أمان الاتصال الآلي منعت استكمال اختبار الاعتماد. لا تتجاوز هذا الحظر.
- إعداد SQL Server الظاهر محليًا: `ForceEncryption=0` ولا توجد شهادة محددة في إعداد المستمع؛ **متطلب TLS لعميل SQL غير مغلق**.
- مراقبة التصدير المحلية `127.0.0.1:3461/api/status` أعادت HTTP 200، ووضع `PARTIAL_REFERENCE_ONLY`، و`readOnly=true`، و1023 من 1024 جدولًا مكتملًا، وجدول واحد متبقٍ، و`baselineComplete=0`. آخر طابع مصدر `2026-11-12T03:13:38.689Z`. هذه حالة مراقبة، **ليست مطابقة مالية نهائية أو اتصال SQL مباشر للوحة**.
- جسر القيادة المحلي `127.0.0.1:8787` يستجيب 503 `OWNER_UID_NOT_CONFIGURED` في endpoint القيادة ومراقبة التصدير؛ لا توجد مصادقة مالك معتمدة.
- بوابة GitHub Pages عامة وثابتة؛ لا يجوز إرسال رمز Firebase إلى `*.github.io/api/...` أو الاعتماد عليه كخادم SQL خاص.

## ما أُضيف في الكود
- جسر `GET /api/jawafa/v1/performance` خلف مصادقة مالك Firebase الحالية، يستخدم upstream محليًا ومحدودًا على `127.0.0.1` فقط، ولا يفتح SQL بنفسه.
- رفض أي استجابة upstream غير موثقة باختبار هوية `user_read` وصلاحيات SELECT المعتمدة ومنع التعديل وتشغيل التشفير والثقة بالشهادة وطوابع الزمن الحديثة.
- بيانات التجميع الخمسة فقط: مبيعات اليوم، مشتريات اليوم، المخزون، الذمم، شيكات تحت التحصيل، مع مقارنة 2025 و2024، واتجاهات أقسام منقّحة، دون كشف السندات والموظفين أو تفاصيل البنوك.
- إضافة بطاقات الأرقام إلى اللوحة المركزية وشاشة ERP 2100، بقيم فارغة `—` حتى ينجح مصدر موثّق. تبقى الاستيرادات المحلية «غير معتمدة».
- إيقاف طلب JWT قبل إرسال أي طلب خاص من موقع GitHub Pages العام.

## شروط الإغلاق المتبقية (الترتيب إلزامي)
1. تشغيل هوية خدمة Windows مستقلة ذات صلاحية قراءة ملف DPAPI محليًا مع عدم عرض كلمة المرور مطلقًا.
2. ربط شهادة TLS موثوقة بعميل SQL وHTTPS الخاص، وفحص تطابق اسم الشهادة وسلسلة الثقة؛ لا تُفعَّل `TrustServerCertificate=True` للإنتاج.
3. إثبات دخول `ORIGINAL_LOGIN()='user_read'` و`DB_NAME()='Jawafa_DB'`، والتشفير والقراءة ومنع DML على كل عرض/جدول مصرح، ومراجعة صلاحيات `db_datareader` الواسعة وتقييدها إلى القائمة المعتمدة.
4. اعتماد SQL views مخصّصة لمؤشرات المبيعات والمشتريات والمخزون والذمم والشيكات والتاريخ؛ لا تخمين لحقول TrustSoft ولا كتابة على الأصل.
5. تشغيل upstream محلي محمي على `http://127.0.0.1:<port>/internal/jawafa/performance` مع سر داخلي محفوظ في الخادم (وليس في المستودع). تمرر الخدمة فقط JSON مجمّعًا مع دليل المصدر وحالة الاختبارات.
6. تهيئة `JAWAFA_SQL_READONLY_UPSTREAM_URL` و`JAWAFA_SQL_GATEWAY_SHARED_SECRET` داخل الخادم فقط. يجب إثبات هوية المالك `JAWAFA_OWNER_UID` عبر Firebase Auth؛ لا يُستخدم البريد بدل UID.
7. نشر موقع وبوابة خاصة على منشأ HTTPS مصادق عليه واحد أو إضافة proxy خاص موثوق؛ GitHub Pages وحده لا يستضيف API. اختبار رفض غير المصرح 401/403 واستجابة 200 بعد دخول المالك وفحص E2E فعلي عبر الكمبيوتر والهاتف.
8. اجتياز تدقيق مستقل وحفظ بصمات الأدلة والاستعادة ومطابقة GATE-15 قبل اعتبار النتائج المالية نهائية.

**الحالة الحالية: CODE_PREPARED / SQL_LIVE_NOT_VERIFIED / PRIVATE_OWNER_AUTH_BLOCKED / HTTPS_SQL_NOT_ACCEPTED.**
