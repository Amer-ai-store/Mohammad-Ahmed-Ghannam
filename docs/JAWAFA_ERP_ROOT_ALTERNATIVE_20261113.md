# JAWAFA / ERP — البديل الجذري للاتصال والتحقق دون فتح قاعدة البيانات

التاريخ: 2026-11-13 · المسار: PR #249 · **لا يُعد اعتماد نشر**.

## لماذا لم يكتمل الربط؟

كانت فجوة التنفيذ الفعلية بين نجاح روابط Flutter ↔ لوحة القيادة وبين نجاح اتصال قاعدة بيانات معتمد في بيئة خاصة. تشغيل GitHub Pages عام وثابت؛ لا يمكنه حفظ اعتماد SQL أو تشغيل DPAPI بأمان. سجلات المشروع بتاريخ 2026-11-12 توثق أن واجهة القراءة المحلية على 127.0.0.1:3467 أعادت ردودًا صحيحة لحالات جزئية مع `user_read`؛ **هذا إثبات تاريخي محدود لا يعني أن النظام يعمل الآن أو أن شهادة SQL موثوقة**. الصلاحيات واسعة بسبب `db_datareader`، وهوية تشغيل Windows والخدمة الخاصة وواجهة المؤشرات الخمسة لم تُقبل.

قناة Remote Desktop Commander الشخصية أظهرت الخادم متصلًا بتاريخ 2026-11-13، ثم أعادت إيقافًا بسبب **سقف الاستخدام الشهري**. لا يجوز إعادة الاتصال لمراوغة السقف أو استنتاج نتيجة SQL من حالة اتصال الجهاز.

## المسار البديل المنفذ في مصدر التطبيق

1. يستمر التنقل بين Flutter ولوحة Amer AI Store المركزية على المسار `#erp-app` في PR #249، دون نسخ قاعدة البيانات أو عرض أرقام تجريبية بوصفها حية.
2. أُضيف `tools/jawafa-readonly-proof.ps1`: مدقق تشغيل محلي **SELECT only** يستخدم PSCredential من `Import-Clixml` تحت هوية Windows نفسها التي أنشأت ملف DPAPI؛ لا يفك كلمة المرور إلى نص صريح ولا يضعها في connection string أو سجل.
3. يُجبر اتصال SQL على `Encrypt=True` و`TrustServerCertificate=False`. نجاح الاتصال هنا يتطلب شهادة TLS صالحة وسلسلة موثوقة واسم خادم مطابق؛ لا يعالج الأخطاء بإلغاء التحقق.
4. يتحقق من `ORIGINAL_LOGIN()=user_read` و`DB_NAME()=Jawafa_DB` والحقوق الفعلية التي يستطيع القارئ الاستعلام عنها؛ يفشل إذا كان عضوًا في `db_datareader` العامة أو `db_datawriter` أو الأدوار الإدارية أو كانت أي صلاحية DML مرصودة. يفحص فقط أسماء views المعتمدة المرسلة صراحة، ويجرب `SELECT TOP (0)` دون قراءة صفوف فعلية.
5. يطبع JSON محدودًا بحالة `BLOCKED` أو `SESSION_GATE_PASS_NOT_RELEASE_APPROVAL`. حتى النجاح **لا يثبت** عدم وجود منح مخفية خارج الرؤية أو قبول التدقيق الأمني المستقل. لا ينتج تقريرًا ماليًا أو بيانات سرية.
6. تراجع `.github/workflows/jawafa-readonly-proof-ci.yml` منطق الفشل الآمن على Windows باستخدام 13 حالة اصطناعية، وبغياب المدخلات. لا تتصل GitHub Actions بخادم المالك ولا تستعمل أسرار SQL مطلقًا.

## التنفيذ الفعلي على الخادم المصرح له — بعد استعادة قناة إدارة مخوّلة

يُراجع المدقق أمنيًا أولًا، ثم تُجرى النسخة المحلية **بواسطة Windows principal الذي أنشأ ملف DPAPI**، واسم SQL Server المطابق للشهادة، وقائمة views المعتمدة من مسؤول قاعدة البيانات. مثال بنيوي بلا قيم حساسة:

```powershell
powershell.exe -NoProfile -NonInteractive -File .\tools\jawafa-readonly-proof.ps1 `
  -ServerInstance "<trusted-certificate-server-name>" `
  -CredentialPath "<DPAPI-file-on-authorized-server>" `
  -ApprovedViews "dbo.<approved-view-1>", "dbo.<approved-view-2>"
```

لا يُنسخ ملف DPAPI ولا كلمة المرور من خادم Windows، ولا تُرفع نتيجة خام أو سجلات خاصة إلى GitHub. يُحفظ الدليل الكامل محليًا في مخزن أدلة محمي، وتُرفق فقط نتيجة منقحة مرجعية وبصمة ووقت تحقق.

**إن لم توجد views محددة/مقبولة أو شهادة موثوقة: النتيجة BLOCKED.** لا تجرّب `sa` أو `TrustServerCertificate=True` لتجاوزها. لا تُعدّل صلاحيات الإنتاج أو شهادة SQL دون موافقة مسؤول الخادم ونسخة إعدادات قابلة للاستعادة.
