# ربط قاعدة SQLite المحلية بلوحة AAS

تعمل هذه الحزمة على الجهاز الذي يستطيع قراءة ملف قاعدة البيانات، وتفتح اتصال HTTPS صادرًا إلى لوحة AAS الخاصة. لا تنشئ خادم HTTP أو منفذًا يستمع داخل الشبكة. العنوان `192.168.1.99:80` وحده لا يحدد نوع قاعدة البيانات أو مكان ملفها؛ لم يثبت اتصال فعلي بهذا الجهاز من بيئة السحابة. لا تظهر القاعدة متصلة في اللوحة إلا بعد وصول ملاحظة حقيقية من الجسر.

المحوّل الحالي يدعم SQLite فقط باستخدام `node:sqlite` في Node 24. لا يتصل MySQL أو PostgreSQL أو phpMyAdmin، ولا يحوّل عنوان HTTP إلى ملف SQLite. إذا كانت القاعدة من نوع آخر، يلزم محوّل مناسب ومعلومات اتصال يحتفظ بها مسؤول الجهاز محليًا.

## ملفات الحزمة

- `integrations/database-bridge/bridge.mjs`: برنامج الاتصال الصادر.
- `integrations/database-bridge/sqlite.example.json`: إعداد افتراضي يرسل الهيكل والأعداد فقط.
- `integrations/database-bridge/inventory.example.json`: مثال اختياري لأعمدة المنتجات والمخزون المسموحة للقراءة والكتابة.
- `integrations/runner/runner.mjs`: قارئ ملف الاتصال الخاص الذي يستورده الجسر؛ يجب الاحتفاظ به في المسار النسبي نفسه عند فك الحزمة.
- `integrations/database-bridge/bridge.test.mjs`: اختبارات فعلية على قواعد SQLite مؤقتة.

## التشغيل الأول دون بيانات صفوف أو تعديل

على الجهاز المحلي ثبّت Node 24، ثم حدد **ملف SQLite الموجود فعلًا** وحساب تشغيل يستطيع قراءته. لا يحتاج البرنامج إلى كلمة مرور قاعدة بيانات SQLite. لا ينسخ ملفات التطبيق أو مفاتيحه إلى اللوحة.

1. أنشئ تعريف جسر SQLite في شاشة قاعدة البيانات باللوحة واحصل على معرّفه.
2. نزّل إعداد الاتصال الخاص من اللوحة واحفظه خارج المستودع، مثل `/home/amer/.config/aas/connection.json` بصلاحية `600`. يضم `baseUrl` و`runnerToken` و`siteAccessToken`؛ لا تضعه في Git أو سجل محادثة.
3. انسخ `sqlite.example.json` إلى ملف محلي، واستبدل `bridgeId` و`databasePath` بالقيم الحقيقية. اترك `readTables` و`writableTables` فارغتين في البداية.
4. شغّل دورة واحدة:

```bash
chmod 600 /home/amer/.config/aas/connection.json
node integrations/database-bridge/bridge.mjs \
  --config /home/amer/.config/aas/sqlite.json \
  --connection-config /home/amer/.config/aas/connection.json
```

يقرأ البرنامج أسماء الجداول والأعمدة وأنواعها وترتيب المفتاح الأساسي وأعداد الصفوف. لا يرسل الصفوف أو أوامر `CREATE TABLE` أو مسار القاعدة المحلي. تُقرأ الملاحظة داخل معاملة SQLite واحدة للاتساق، وتبقى القاعدة دون تعديل في هذا الوضع. لا يُنشأ ملف قاعدة جديد إذا كان المسار غير موجود.

ملف الاتصال نفسه الذي يستعمله منفّذ AAS صالح للجسر. يمكن أيضًا ضبط `AAS_BASE_URL` و`AAS_RUNNER_KEY` و`AAS_SITES_AUTHORIZATION` في بيئة الحساب؛ تتقدم قيم البيئة على الملف. تُرسل الأسرار في ترويستي `X-AAS-Runner-Key` و`OAI-Sites-Authorization` إلى أصل HTTPS المحدد فقط، دون اتباع تحويلات. لا يحتاج الجسر إلى مفتاح الخدمة العام الذي يتيح قراءة بيانات المتجر.

لتكرار الدورة كل دقيقة أضف `--watch --interval 60` إلى الأمر نفسه. المدى المسموح للفاصل ١٠–٣٦٠٠ ثانية. الفشل في الشبكة قبل قراءة السياق/إرسال الملاحظة يوقف الدورة قبل أي تعديل محلي. يمكنك تشغيل الأمر بخدمة نظام تحت حساب مخصص بعد مراجعة الصلاحيات. لا يلزم فتح المنفذ 80 أو نشر ملف SQLite على الشبكة.

## اختيار بيانات المنتجات

لا تُرسل بيانات صفوف افتراضيًا. بعد التأكد من أسماء الجداول الفعلية، يمكن إضافة قائمة محلية صريحة مثل:

```json
{
  "readTables": [
    { "name": "products", "columns": ["id", "name", "price", "stock"], "limit": 25 }
  ]
}
```

هذه أسماء توضيحية؛ يجب أن تطابق القاعدة الحقيقية. لا يكفي تغيير شاشة اللوحة لتوسيع صلاحيات القراءة. يمنع محوّل المخزون أسماء جداول/أعمدة العملاء والعناوين والبريد والهاتف والبطاقات وCVV وكلمات المرور والرموز والأسرار. الملفات الثنائية لا تُنقل، والنصوص تُنقّى من محارف التحكم وتُختصر إلى ٢٥٦ حرفًا لكل خلية. لا تختَر وصفًا أو عمودًا يحتفظ بمعلومات شخصية.

حد الصفوف ١٠٠ لكل جدول و٥٠٠ إجمالًا، وحجم الملاحظة الصادرة ١٩٠ KiB. يبقى حد الخادم مستقلًا عند ٢٢٠٬٠٠٠ بايت. يوجد حد ١٠٠ جدول و١٠٠ عمود لكل جدول في قراءة الهيكل. يُعدّ كل جدول حتى ١٠٠٠٠١ صف فقط؛ إذا بلغ العد هذا الحد تظهر `rowCountCapped: true`، فيصبح العدد حدًا أدنى لا إجماليًا كاملًا. القاعدة المحلية نفسها محدودة إلى ١ GiB في هذا الإصدار.

## تمكين كتابة محددة

لا تطبق الواجهة أوامر SQL، ولا ترسل مسار قاعدة أو شيفرة لتنفيذها. يستطيع المسؤول وضع عمليات `insert` أو `update` أو `delete` منظمة في الطابور. يظل التنفيذ محكومًا بقائمة محلية يراجعها مسؤول الجهاز، وبخيار `--apply` الصريح.

```json
{
  "backupDirectory": "/var/backups/aas-sqlite",
  "writableTables": [
    { "name": "products", "columns": ["name", "price", "stock"], "primaryKey": ["id"] }
  ]
}
```

تشغّل الكتابة بالأمر السابق مع إضافة `--apply`. دون هذا الخيار تبقى العمليات معلقة، ولا يُنشأ سجل داخلي أو نسخة احتياطية أو تعديل بيانات. تتضمن الملاحظة قائمة الكتابة المحلية لتوضيحها في اللوحة؛ تظل الحماية المحلية هي المرجع عند وصول العملية.

تحتاج عمليات التحديث والحذف المفتاح الأساسي الكامل؛ يتحقق الجسر من تطابقه مع تعريف SQLite الحقيقي، بما في ذلك المفاتيح المركبة وترتيبها. لا يمكن تغيير المفتاح عبر تحديث، ولا إجراء تحديث/حذف جماعي. يستخدم الإدراج الأعمدة المسموحة فقط، ويمكن ترك معرّف SQLite التلقائي خارج الأعمدة المسموحة. القيم تُربط بمعاملات SQL؛ النص الذي يشبه SQL يُعامل كقيمة نصية ولا يُنفّذ. لا توجد واجهة SQL عام أو shell أو تنزيل patch في هذا المحوّل.

مثال عملية تحديث يرسلها الطابور:

```json
{
  "id": "operation-EXAMPLE",
  "action": "update",
  "table": "products",
  "key": { "id": 42 },
  "values": { "stock": 15 }
}
```

قبل كل عملية مقبولة تُنشأ نسخة SQLite متسقة باستخدام واجهة backup الأصلية، داخل مجلد محلي بصلاحية خاصة؛ ملف النسخة بصلاحية `600`. تحتوي النسخة القاعدة المحلية كاملة، لذا احتفظ بها محليًا ولا ترفعها إلى اللوحة. إذا فشل النسخ لا تُنفَّذ العملية.

تُنفَّذ العملية داخل معاملة واحدة مع تسجيل نتيجتها في جدول تقني ثابت `_aas_bridge_operations` داخل **القاعدة نفسها**. يظهر هذا الجدول فقط عند تصريح الكتابة، ويُستبعد من الهيكل والصفوف المنشورة. يضمن جمع التغيير والإيصال في المعاملة نفسها أن انقطاع البرنامج بين التعديل والإقرار لا يعيد الإدراج/التحديث في التشغيل التالي. لا يُعتمد على سجل منفصل قد يختلف عن القاعدة بعد تعطل أو استخدام WAL.

يعيد الجسر `applied` فقط بعد نجاح `COMMIT` وتغيير صف مباشر واحد. تُرفض المدخلات المخالفة محليًا دون تغيير بيانات، ويُعاد `failed` بعد تراجع المعاملة إذا رفضت SQLite القيود أو لم يُطابق المفتاح صفًا. رقم `changes` يصف الصفوف المباشرة التي غيّرها الأمر؛ قد تنفّذ triggers الموجودة في القاعدة آثارًا أخرى ضمن المعاملة نفسها. الإيصال يحوي بصمة العملية وحالة النسخ، ومع الإدراج قد يحوي `lastInsertRowid` الذي أبلغت عنه SQLite، دون نسخ محتوى الصف.

فقدان إقرار الشبكة يُبقي الإيصال في السجل المحلي. تُعاد محاولة **إرسال الإيصال** في الدورة التالية؛ يُعاد استعمال نتيجته الأصلية دون تنفيذ العملية مرة أخرى. إعادة معرّف العملية بقيم مختلفة تُرفض. لا تحذف جدول السجل أو تستعد نسخة قديمة بينما الجسر يعمل؛ أوقفه وراجع الطابور والإيصالات قبل أي استعادة لقاعدة قديمة.

## بروتوكول الاتصال

كل المسارات التالية ضيقة ومحمية بمفتاح المنفّذ والبوابة الخاصة:

| المسار | الوظيفة |
| --- | --- |
| `GET /api/v1/bridge/context?bridgeId=...` | تعريف الجسر المفعّل وحتى ٢٠ عملية معلقة؛ لا يعيد مسارات أو أسرار قاعدة البيانات. |
| `POST /api/v1/bridge/snapshot` | `{bridgeId,snapshot}` يتضمن ملاحظة حقيقية وهيكلًا وأعدادًا وعيّنة المخزون المحددة محليًا. |
| `POST /api/v1/bridge/receipts` | `{bridgeId,receipt}` يتضمن `operationId,status,observedAt,changes,backupCreated,summary,operationDigest` و`lastInsertRowid` الاختياري. |

إرسال الملاحظات والإيصالات لا يستخدم مراجعة حالة المتجر العامة؛ يتابع الخادم سجل الجسر وطابوره منفصلين. لا يعني وصول ملاحظة أن عنوان HTTP المحلي متاح، أو أن تطبيق Android اتصل، أو أن عملية دفع/تسليم تمت. لا تُسجَّل كتابة ناجحة في اللوحة قبل وصول إيصال تطبيق فعلي.

التحقق داخل مشروع مركز القيادة:

```bash
node --test integrations/database-bridge/bridge.test.mjs
```

تشغّل الاختبارات SQLite فعلية في ملفات مؤقتة، وتفحص النسخ والرجوع عن القيود ومنع حقن SQL ومنع إعادة تنفيذ العملية عند فقدان الإقرار. لا تتصل الاختبارات بقاعدة الجهاز `192.168.1.99` ولا تعدّلها.
